# Diffie-Hellman Key Exchange · MITM Attack · PKI Authentication

A hands-on demonstration of why plain Diffie-Hellman key exchange is vulnerable to Man-in-the-Middle (MITM) attacks, and how a Public Key Infrastructure (PKI) — CA-issued certificates and digital signatures — closes that gap. Built as a mini project for a Cryptography and Network Security course.

The project has two parts:
1. **Python socket implementation** — real TCP processes (Alice, Bob, and Mallory) demonstrating the attack and the fix over an actual network connection.
2. **Interactive browser GUI** — a single HTML file that runs the same concepts visually, with real 2048-bit Diffie-Hellman, RSA-PSS signatures, and AES-GCM encryption via the Web Crypto API.

## 🖥️ Part 1: Interactive GUI (easiest way to explore this project)

Open `dh_mitm_visualizer.html` directly in any modern browser — no server, no install, no dependencies.

**Features:**
- Two toggles: **Attacker Present** and **Authentication (PKI) Enabled** — combine them to reproduce all four demo scenarios
- Live animated visualization of Alice, Bob, and Mallory exchanging DH values, certificates, and encrypted messages
- Real cryptography running client-side: 2048-bit Diffie-Hellman, RSA-PSS signatures, AES-256-GCM
- Full run history — every run you execute stacks up with a labeled card (settings, message sent/received, verdict), so you can compare a blocked attack against a successful one side by side without losing context
- Word-level diff highlighting shows exactly what Mallory tampered with when an attack succeeds

Just double-click the file, or right-click → Open With → your browser.

## 🐍 Part 2: Python Socket Demos (real network processes)

### Prerequisites

```bash
pip install cryptography
```

### A. Unauthenticated demo (`socket_demo/`) — attack succeeds

**Baseline — no attacker:**
```bash
cd socket_demo

# Terminal 1
python3 bob_server.py

# Terminal 2 (after Bob is listening)
python3 alice_client.py --port 6000
```

**With Mallory — attack succeeds silently:**
```bash
# Terminal 1
python3 bob_server.py

# Terminal 2 (after Bob is listening)
python3 mallory_proxy.py

# Terminal 3 (after Mallory is listening)
python3 alice_client.py --port 6500
```

Mallory establishes two independent shared secrets (one with Alice, one with Bob), decrypts Alice's "secret" message, tampers with it (changes the PIN from `4471` to `9999`), and Bob decrypts the tampered version believing it's authentic.

### B. Authenticated demo (`socket_demo_secure/`) — attack is blocked

**Run once, to generate the CA and certificates:**
```bash
cd socket_demo_secure
python3 setup_ca.py
```

**Baseline — no attacker:**
```bash
# Terminal 1
python3 bob_server_secure.py

# Terminal 2
python3 alice_client_secure.py --port 7000
```

**With Mallory — attack is detected and blocked:**
```bash
# Terminal 1
python3 bob_server_secure.py

# Terminal 2 (after Bob is listening)
python3 mallory_proxy_secure.py

# Terminal 3 (after Mallory is listening)
python3 alice_client_secure.py --port 7500
```

Mallory attempts the identical interception strategy. Bob's signature verification rejects her forged DH value before responding. Her fallback — requesting her own honest certificate — only succeeds in identifying her transparently as "Mallory," never as "Alice." Alice's message is never delivered.

> **Note (Windows):** use `python` or `py` instead of `python3` if `python3` isn't recognized.

## 🧠 How It Works

### The vulnerability
Plain Diffie-Hellman lets two parties agree on a shared secret over a public channel, but provides no way to verify **who** sent each public value. An attacker positioned on the network path can intercept both sides' public values, substitute their own, and establish two separate shared secrets — one with each victim — without either party noticing.

### The fix
Each party's ephemeral DH public value is signed with their long-term private identity key, and sent alongside a CA-issued certificate binding their identity to that key. The receiver verifies:
1. The certificate is validly signed by the trusted CA.
2. The DH value's signature verifies against the certified public key.

An attacker without the victim's private key cannot forge a valid signature, so a substituted DH value is rejected before any secret is ever shared with them — exactly how TLS defeats MITM attacks against HTTPS today.
